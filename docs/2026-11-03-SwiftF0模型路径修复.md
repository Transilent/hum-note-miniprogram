# SwiftF0 模型路径修复 · 2026-11-03

用户手机截图中的具体错误为 `createInferenceSession:fail:model path invalid : %s`。这说明加载停在模型文件路径处理阶段；该错误不能用于判断手机硬件、SwiftF0 算子或识别准确度。

上版将 `models/swift-f0-cnn.onnx` 这样的代码包相对路径直接交给原生接口。截图尚不能区分相对路径解析问题与独立 `.onnx` 文件打包问题。本版同时绕开这两个环节，改为将模型以普通 JavaScript 数据模块随包携带，再写入微信本地数据目录。

## 手机复测

1. 用更新后的工程重新生成预览；本版诊断版本为 **`0.3.0-wechat-v3`**。
2. 首页选择 **SwiftF0 · 实验 → 检查实验识别兼容性**。请运行新的检查，不要以旧灵感里保存的旧诊断判断修复结果。
3. 若检查通过，再录一小段哼唱，确认编辑页显示 **SwiftF0 实验**。
4. 若检查失败，点击“复制报告”，发回完整文字。报告会包含实际使用的本地文件路径、大小、模型 SHA256、缓存状态，以及失败的检查阶段。

本版已验证微信开发者工具中的实际文件准备与回读，**尚未在用户的 vivo X200 Ultra 上验证原生模型加载和推理成功**。模拟器仍会明确报告“不支持此 API 调试”，这与手机截图的路径错误不同。

## 加载方式

- 模型以 `swift-f0-cnn-data.js` 和 `inference-probe-data.js` 携带，内容是模型字节的 Base64 编码，避免依赖独立 `.onnx` 资源的打包规则。不会从网络下载模型。
- 首次使用时，在 `wx.env.USER_DATA_PATH + '/humnote-models/'` 下生成真实 `.onnx` 文件，原生接口使用该文件的完整本地路径。文件名带模型哈希，版本间不会混用。
- 写入先经过临时文件，再重命名并回读逐字节校验。后续使用先验证缓存；即使缓存长度正确但内容损坏，也会重建。操作仅针对哼记自己生成的模型缓存，不修改灵感或录音。
- 已修正微信跨运行环境缓冲区的判断：真实 `FileSystemManager` 回读得到的 ArrayBuffer 可能不满足当前环境的 `instanceof ArrayBuffer`。模型文件与推理输出改用兼容的类型判断。
- 诊断分别记录文件准备、加载、运行和输出错误。遇到 `model path invalid` 时明确说明文件路径问题，不再暗示设备或算子不支持。

首页仍不加载实验模型数据或创建推理会话；数据模块仅在实验识别或兼容性检查时使用。本地模型缓存占约 81 KiB，JS 编码会增加约 110 KiB 的源文件体积。运行小程序不需要 npm 或 Python 依赖。

## 验证

- **176 项命名回归检查通过**，其中 34 项为实验识别、模型文件与诊断检查。
- 新增/更新检查覆盖：JS 模型字节与 ONNX 原文件哈希一致、本地完整路径、缓存命中、同长度损坏缓存修复、空间不足、展开截断、重命名失败后清理与重试，以及跨运行环境 ArrayBuffer。
- 在实际微信文件系统写入并回读了 **136 字节的最小测试模型**和 **82,484 字节的 SwiftF0 CNN**。微信原生文件 API 的大小、MD5 摘要与工程原文件均一致。
- 模拟器诊断已通过两个文件的准备，向原生接口传入本地路径；随后返回开发者工具不支持推理 API，未冒充手机推理成功。
